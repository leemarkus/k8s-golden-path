# ADR-0011 — Generate tenant availability and latency SLOs

## Status

Accepted design; implemented by the observe stage.

## Date

2026-10-03

## Context

Ingress-nginx already exports request counters and duration histograms, so static tenants need no app metrics. The hand-written SLO file explicitly asks to revisit generation beyond roughly five SLOs: three platform SLOs plus two tenant objectives per environment cross that threshold.

## Decision

The observe stage generates recording/alert rules for each tenant/env from one tested arithmetic implementation. Filter ingress metrics by namespace `<tenant>-<env>` and ingress name `<tenant>`; never aggregate other tenants into its budget. Availability bad fraction = 5xx requests / all requests. Latency bad fraction = 1 - duration bucket count at `le="0.5"` / duration count. Initial explicit priors: availability 99.5%, latency 99% within 0.5s over a nominal 30-day budget; do not call them measured targets.

For each SLI calculate error ratio at 5m, 30m, 1h, 2h, 6h, 1d and 3d. Burn = ratio / (1 - objective). Critical arms: (5m AND 1h >14.4) OR (30m AND 6h >6). Warning arms: (2h AND 1d >3) OR (6h AND 3d >1). Both windows must cross their threshold. Labels include tenant, env, slo, severity; PrometheusRule carries `release: kube-prometheus-stack`. Place rules and dashboard ConfigMaps in the tenant namespace; verify Prometheus namespace selection at live activation. Dashboard ConfigMaps use `grafana_dashboard: "1"`.

Zero traffic is no observation, not perfect availability: denominator >0 gates burn calculations. An absent ingress series/histogram gets a separate telemetry diagnostic with a startup grace period (15m), not a fabricated success. Keep failed-request series fallback scoped to the denominator’s tenant. Low traffic remains explicitly visible on dashboards. Seven-day retention cannot substantiate an observed 30-day compliance claim.

An earlier lab decision declined lab-wide p99 alerts because the traffic was probes. We generate a threshold-fraction latency contract for the new real tenant, but live activation must measure real user traffic and validate buckets before enabling latency paging; otherwise retain recording/dashboard output and mark latency paging unactivated. This is a deliberate staged qualification, not evidence that the earlier decision's conditions are already met. App ServiceMonitor is optional only for actual /metrics. Logs inherit cluster-wide Alloy → Loki; no per-tenant log agent.

## Alternatives considered

- **Copy hand-written SLO rules per tenant:** Rejected. Crosses the lab’s own generation threshold and duplicates arithmetic/selector mistakes.
- **Require app metrics for all SLIs:** Rejected. Static nginx exposes no application metrics; ingress measures user-visible backend errors consistently.
- **Install Sloth/Pyrra or add p99 paging immediately:** Rejected. Adds dependencies/runtime without need and ignores the earlier decision's traffic evidence; p99 is not an error-budget fraction.

## Consequences

The observe stage owns deterministic generation tests, including cross-tenant isolation, no traffic, absent telemetry and each burn window. Latency activation remains conditional on live activation measurements; availability at low volume is also a prior.

## Evidence

Sources are the lab's private repositories (cluster GitOps, alert routing, the reference service and the SRE agent); their paths are omitted from this public copy.

## Verification

The observe stage tests formula outputs at boundaries and generated selectors; promtool is currently absent. Live activation inspects loaded rules, series, buckets and a controlled burn/absence alert drill before claiming live observability.

## Implementation notes (the observe stage, 2026-10-03)

One deterministic authoring helper, `templates/observe/generate.mjs`, produces
checked-in JSON-subset YAML templates and proposed promtool fixtures. The gp
renderer remains unchanged. The template contract supplies `env` only to deploy
overlays; instead of adding an undocumented placeholder or requiring a shared
CLI change, the observe root is explicitly the dev bundle and `observe/prod/`
is the independent prod bundle. The deploy stage must include each from its matching
overlay, not the shared base. Exact resource-list integration edits and
activation steps are in `templates/observe/README.md`.

Selector clarification: the reference SLO rule verifies request/status metric
names and burn arithmetic, but aggregates the whole controller, not a tenant
namespace. Its diagnostic uses `exported_service`, evidence of scrape-label
collisions. Tenant queries therefore union exact `exported_namespace` matches
with native `namespace` matches only when `exported_namespace` is absent/empty,
always also matching `ingress`. This preserves backend identity under either
label convention without mistaking a scrape namespace for a tenant. Alternatives
were assuming native namespace always survives (risk of silent empty SLIs), or
changing the platform ServiceMonitor's honorLabels setting (outside this repository).
Live labels still require live activation verification; none were inspected here.

Both recording SLIs gate on positive traffic; availability's zero-failure fallback
is derived from its own denominator. Separate 15m diagnostics distinguish absent
requests, absent latency count/bucket, and present-but-idle counters. Burn
arithmetic, strict comparisons and `for` durations match the lab rules.
Dashboards expose low volume, no observation and a trailing-3d budget estimate,
not observed 30-day compliance. All resources include the relevant rule or
sidecar discovery labels; chart defaults/live namespace discovery remain an
activation check because the values files do not explicitly set those selectors.

Latency burn rules are generated under each bundle's excluded `staged/` directory
with an additional false expression gate. Recordings and quantiles remain in the
default bundle. Real user ingress traffic, measured latency distribution, a
verified threshold bucket and a reviewed objective are required for live activation to
activate them, preserving that earlier decision. Availability/diagnostic alerts also carry a
temporary publication gate for the ADR-0012 reason below. The optional app
ServiceMonitor is excluded, requires an opt-in Service and named metrics port,
and inherits platform scraping rather than installing another metrics stack.

Node tests independently derive all multipliers from 30-day budget fractions,
exercise changed objectives and paired-window comparisons, parse all rendered
templates and check labels, selectors, missing-data guards and fixture generation.
Proposed promtool tests include counter resets, data absence and cross-tenant
negative controls. `promtool` is absent; those engine-level checks are unexecuted.
